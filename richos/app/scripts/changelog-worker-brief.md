# Changelog worker: <TAG>

Prepare the notes for candidate <TAG> from the request at `<REQUEST>`. The candidate is not published. Write on your own branch only, then hand over to Rich. Never commit or push main, publish a build, touch the CEO's app or phones, launch an app or change the host display.

## Draft before publication

1. Read the request and `richos/app/scripts/changelog-instructions.md`. Pin its source commit and previous successfully published source. Start from `changed_files`, the exact net implementation inventory, including deleted files. The compact `changes` history contains ordinary commits and merges as lookup aids. Read full commits only when useful; their subjects and bodies are authors' accounts, not established release facts. For a request made by older tooling, obtain the net inventory with `git diff --no-renames --name-status <previous_source> <source_commit>`; if there is no previous release, use `git ls-tree -r --name-only <source_commit>`.
2. Establish what changed before writing any public line. Work through the inventory by product area. Read `git diff <previous_source> <source_commit> -- <paths>` and the relevant source at those exact commits (`git show <commit>:<path>`), following callers and consumers far enough to establish the actual behavior, actors and conditions. Read existing acceptance evidence where it applies. Your current checkout may be newer; never describe its later behavior. Do not run application tests or launch an app for prose.
3. Keep a concise `facts.md` beside the request, outside the repository and sealed candidate. Account for all changed files in groups: the user-visible result, combined with another result or excluded with a reason. Establish before/after behavior and its scope for every included result, backed by what the implementation and acceptance evidence actually show. Check removed and reverted behavior. Resolve gaps before writing; report a genuine unresolved fact to Rich without inventing it or silently dropping the affected user change. Preserve this account for the handover.
4. Write the user-facing bullet lines to a file in your SSD scratch directory from those established facts. Consolidate related changes and exclude internal work. A nightly compares with the previous published nightly; a stable compares with the previous published stable, covering all intervening nightlies. Do not copy only the promoted nightly's incremental entry. If nothing user-visible changed, the prescribed fallback is valid only after accounting for the inventory.
5. In your work branch, run `python3 richos/app/scripts/nightly.py notes-draft --request <REQUEST> --entry <your-bullet-file>`. This writes the exact entry and candidate record in `docs/release-notes.json`. It refuses stale requests and main. Do not edit the record by hand. A stale baseline means Rich regenerates the request against the current published channel and you update the facts and prose for that range.
6. Inspect the diff. It must contain only the corresponding changelog and candidate record. Commit the two files, merge local main into your branch once and hand over the branch, commit, candidate identity, baseline, complete entry and private facts-account path. Newt owns both factual accuracy and complete coverage of user-visible changes; another worker is not assigned to supply either afterward.

## Lead: finish this job without involving the CEO

Use the exact dispatch command: it selects `--type newt`, with Opus for every task, whether nightly or stable and points at this brief with its tag and request already filled in. Do not substitute a generic engineer or leave the writer choice to memory.

A usage hold delays this work and publication; it must never leave a public release without its notes. A dispatch error is unresolved work, not a successful release. The request and dispatch receipt survive in the nightly state directory outside the sealed candidate.

Keep the draft on its branch until QA accepts this exact candidate. If QA rejects it, discard that draft and close its escalation. Never land a rejected candidate's entry. The replacement gets a new request from the last successfully published release, so rejected changes are not lost or marked announced.

Once QA accepts the candidate and Newt has finished its source-grounded entry and coverage account, land and push the approved entry and record together through the ordinary gate. Only Rich lands main. As the very next step, run `nightly-local.py publish --run <the request's candidate run>` yourself. Publication reads remote main and refuses absent, mismatched or stale notes before creating a public tag or release. The GitHub release body carries the same approved prose from its first public appearance. Do not ask the CEO to approve changelog mechanics or remind you to resume.

A failed upload keeps the same candidate and approved notes. Retry publication; never rebuild, allocate another version, rewrite the body or rerun QA merely because an upload failed. Keep this same job open until the release body and installable channel have been verified. If the candidate is deliberately abandoned after its notes landed, remove its entry and record through the normal gate before closing the job. The entry carries its own GitHub release link.
